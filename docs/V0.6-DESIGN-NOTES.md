# v0.6 Design Notes

## 1. Compatibility is now a first-class plane

Earlier versions treated upstream compatibility as a release note/limitation.

v0.6 promotes it to executable architecture:

```text
upstream baseline
→ environment doctor
→ real install probe
→ hook graph assertion
→ semantic acceptance
```

## 2. Why there are three levels

A single E2E status would create false confidence.

### L0

Can prove:
- our scripts run;
- our hook expectations are internally consistent;
- ship/release/mutation deterministic contracts still pass.

Cannot prove:
- real GSD accepts a manifest;
- Claude dispatches a skill;
- gstack opens a browser;
- Superpowers obeys the routing boundary.

### L1

Uses real GSD to prove:
- local third-party capability lifecycle;
- project consent/activation;
- staged bundle;
- registry composition;
- hook point existence;
- hook ordering;
- third-party gate visibility.

Still cannot prove LLM/skill semantics.

### L2

Proves the behavioral seam with actual Claude Code/gstack/Superpowers.

This is where upstream skills keeping the same filename but changing behavior are caught.

## 3. `--yes` is intentional in disposable L1

Current GSD capability install is non-interactive.

A capability with executable surfaces aborts unless `--yes` grants consent.

L1 runs in a disposable fixture and passes `--yes` explicitly so a CI-compatible
probe can reach activation/rendering.

This must not be generalized to arbitrary third-party capabilities.

## 4. Project consent is part of the test

GSD project-scope overlays can exist on disk but remain `inactive` if this machine
has no matching user-owned consent record.

L1 asserts:

```text
capability list
status == active
```

not merely "directory exists".

## 5. Node requirement drift was discovered by the harness work

Current GSD 1.10 package metadata says:

```text
node >=24
npm >=10
```

Some upstream installation documentation still states Node 18.

For executable compatibility, v0.6 follows package engine metadata and fails
closed below Node 24.

This is a concrete example of why compatibility assumptions belong in code.

## 6. Hook graph is treated as API

L1 asserts these surfaces:

```text
plan:post
execute:wave:pre
execute:post
verify:pre
ship:pre
ship:post
```

and the Triple Crown entries inside them.

If GSD renames a point, changes third-party generic dispatch, or changes artifact
ordering semantics, L1 fails before a user discovers it in a production project.

## 7. Behavioral contracts cannot be reduced to grep

v0.6 does not declare gstack/Superpowers compatible merely because skill names
exist.

The doctor checks install/surface presence. L2 verifies the semantics:

```text
qa-only does not fix
document-release may mutate docs
canary requires a deployed URL
Superpowers selected disciplines do not become lifecycle owners
```

## 8. Fixture has a deliberate defect

The logout defect creates two useful acceptable paths:

```text
review catches/fixes
→ mutation + stale evidence path

OR

review leaves it
→ qa-only finding + UAT gap path
```

This avoids overfitting acceptance to a specific probabilistic reviewer outcome.

## 9. Next step after v0.6

Do not add v0.7 features before a real L1/L2 run.

Recommended next action:

```text
Windows/WSL or Linux target
Node 24
real GSD 1.10
real Claude Code
real gstack
real Superpowers
disposable GitHub repo
→ run v0.6 acceptance
```

Only after that should the next design slice address:
- provider-native deployment evidence (Vercel/AWS/GitHub Deployments);
- explicit PR merge governance;
- Canary alert → incident/remediation phase bridge.
