# v0.6.3 Design Notes — Distribution / Installer

## Problem

The previous prototype required the user to manually run:

```text
gsd capability install triple-superpowers
gsd capability install triple-gstack
gsd capability install triple-crown-guide
node install-claude-ship-guard.cjs
merge CLAUDE routing
```

That is too many installation seams for a workflow whose purpose is reducing
operational cognitive load.

## Decision

Expose one install CLI:

```text
triple-crown
```

distributed as a normal npm `bin` package.

Primary UX after publish:

```bash
npx --yes triple-crown-workflow-installer@latest install --yes
```

The same CLI is wrapped by `install.sh` and `install.ps1`.

## Stable project source

A critical issue with naive `npx` capability installation is that npm executes
the package from a cache/temp directory.

GSD project capability source records must not depend on that temporary path.

Therefore installation first vendors runtime sources into:

```text
.triple-crown/
```

and registers capabilities from:

```text
./.triple-crown/capabilities/<id>
```

The npm cache can disappear without making the project capability source path
invalid.

## Refresh behavior

Re-running install:

```text
copies the new stable source
→ removes previous Triple Crown project capability registration
→ installs the current local stable capability
→ verifies `capability list` reports ACTIVE
→ replaces only the managed CLAUDE routing block
→ idempotently refreshes the ship guard
```

Runtime data under `.planning` is not purged.

## Dependency policy

### GSD

When missing and bootstrap is enabled:

```bash
npx --yes @opengsd/gsd-core@latest --claude --global
```

The installer then resolves either the public CLI or the installed
`gsd-core/bin/gsd-tools.cjs`.

### gstack

When missing:

```text
clone ~/.claude/skills/gstack
run setup --host claude --no-prefix
```

Short IDs are intentional because Triple Crown defaults to:

```text
review
qa-only
cso
canary
document-release
retro
```

### Superpowers

Do not pretend to own the Claude plugin marketplace.

Official Claude install remains:

```text
/plugin install superpowers@claude-plugins-official
```

Normal install warns when it is absent.

```text
--strict
```

turns that warning into a hard dependency gate.

## Consent

GSD third-party capabilities require explicit executable-surface consent.

The Triple Crown installer therefore asks once in an interactive terminal and
then passes GSD's `--yes` to each known bundled capability.

Non-interactive runs require the user's explicit:

```text
--yes
```

This preserves a visible consent boundary instead of silently bypassing it.

## Uninstall ownership

Triple Crown uninstall removes only surfaces it owns:

```text
Triple Crown capability registrations
.triple-crown/
managed CLAUDE.md marker block
Triple Crown ship guard hook/registration
```

It does not uninstall:

```text
GSD
gstack
Superpowers
```

## Packaging

The package exposes aliases:

```text
triple-crown-workflow-installer
triple-crown
triple-crown-install
```

The shorter `triple-crown` name is used for local tarball tests because it is
stable even if the package is later published under an npm scope.

## Validation

Executable fixture tests cover:

```text
direct Node CLI install
idempotent reinstall
workflow status after install
uninstall
local bash wrapper
local npm .tgz through npx --package
```

The actual remote bootstrap of current GSD/gstack remains a target-host test
because the artifact environment is below GSD's Node 24 runtime requirement.
