# v0.5 Design Notes

## 1. Hard guard moved from policy to execution

Earlier versions said:

```text
do not use gstack /ship
```

in project routing.

v0.5 retains that instruction but also installs a Claude Code `PreToolUse(Bash)`
hook. The hook blocks the remote effects of an alternate ship lifecycle.

This is stronger because it still applies under permissive/bypass permission
modes.

## 2. Why the guard protects effects rather than the Skill tool

Claude Code hook matchers reliably expose Bash/tool calls, while shipping ultimately
requires observable remote-effect commands such as `git push` and `gh pr create`.

Blocking those effects is runtime enforcement independent of how the model arrived
at the command.

## 3. GSD ship itself performs multiple pushes

Current GSD ship pushes:
- the feature branch;
- later a STATE.md shipping-note commit;
- in a CI wedge case, a recovery empty commit.

The authorization therefore permits several pushes but only one PR creation.

The authorization is session-bound after the first protected action and expires
quickly.

## 4. ship:post is not post-deploy

This is the most important v0.5 correction.

Current GSD creates the PR, tracks shipping, then dispatches `ship:post`.

gstack Canary explicitly requires a live URL and post-deploy semantics.

Therefore:

```text
ship:post
  -> RELEASE ledger
  -> canary only if deployment evidence already exists
```

Most real runs will defer Canary until `release-observe`.

## 5. document-release is a controlled post-gate mutation

Upstream gstack document-release can:
- edit docs;
- commit;
- push;
- update the PR body.

That happens after GSD ship gates, so v0.5 does not treat it as unrestricted
mutation.

It is allowed only under a path-restricted push authorization. VERSION remains
outside the default allowlist.

If a docs commit changes the PR head, RELEASE.json is recaptured and any prior
deployment SHA no longer matches automatically.

## 6. Retro remains advisory

Upstream retro defaults to a 7-day engineering retrospective. Running it on every
PR would distort its intended time-window semantics.

Default is manual.

## 7. Remaining v0.6 candidates

- GitHub deployment/status connector adapter
- provider-specific deployment evidence (Vercel/AWS/etc.)
- explicit PR merge ownership capability
- incident workflow from Canary alerts
- release history across phases/milestones
