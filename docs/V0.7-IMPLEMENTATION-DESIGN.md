M-1 완료 후에야 §2.1 백업 → §2.2 제거 → M0 순으로 진행한다.

### 2.0.1 백업·제거 수행 시점

M0 착수 **전에** 수동 수행. 파괴적 작업이므로 백업이 선행한다.

### 2.1 백업 — 매니페스트 방식

텍스트 2개만 복사하는 것으로는 부족하다. 제거 대상 6곳 **전부**를 버전된 아카이브 + 매니페스트로 보존한다. `scripts/legacy-backup.cjs backup` 이 수행한다.

산출물: `~/.crew-legacy-backup/2026-08-20/`

```
archive.tar.gz            제거 대상 전체 트리 (경로 보존)
MANIFEST.json             { path, kind, sha256, bytes, mode } 목록 + 복구 순서
CLAUDE.md.fragment        ~/CLAUDE.md 에서 제거할 마커 블록 원문 (시작/끝 행 번호 포함)
settings.json.hookgroup   제거할 PreToolUse 훅 그룹 **객체 원문** (배열 인덱스 미사용)
restore.sh                이 백업만으로 원상 복구하는 실행 가능 스크립트
```

매니페스트에 담기는 대상:

| 경로 | 보존 방식 |
|---|---|
| `~/.gsd/capabilities/{triple-gstack,triple-superpowers,triple-crown-guide}` | 디렉터리 전체 (파일별 sha256) |
| `~/.triple-crown/` | 디렉터리 전체 |
| `~/.claude/hooks/triple-crown-ship-guard.cjs` | 파일 |
| `~/CLAUDE.md` | 파일 전체 + 마커 블록 분리 추출 |
| `~/.claude/settings.json` | 파일 전체 + sha256 + 훅 그룹 객체 분리 추출 (인덱스 미사용) |
| `~/.claude/skills/` 중 `.crew-skill`·`.triple-crown-skill` 마커 보유 디렉터리 | 디렉터리 (현재 0개, 있으면 포함) |

### 2.1.1 사전 점검 — 다른 프로젝트 영향

제거는 **머신 전역** 라우팅과 ship 가드를 없앤다. 백업 직후, 제거 직전에 확인한다:

```
find ~ -name STATE.md -path '*/.planning/*' -not -path '*/node_modules/*' 2>/dev/null
```

결과가 비어 있지 않으면 각 프로젝트의 `.planning/STATE.md` 를 열어 진행 중 phase가 있는지 확인한다. 하나라도 있으면 **제거를 보류**하고, 해당 프로젝트를 먼저 phase 경계까지 정리한다.

### 2.2 제거 대상 6곳

```
1. gsd-tools capability remove triple-gstack       (스코프 자동 판별)
                        remove triple-superpowers
                        remove triple-crown-guide
2. ~/CLAUDE.md 의 <!-- triple-crown:managed-routing:start --> ~ :end 블록
   → 마커 쌍 사이만 제거. 사용자 작성분 보존
3. ~/.claude/hooks/triple-crown-ship-guard.cjs
4. ~/.claude/settings.json 의 PreToolUse(Bash) 훅 등록 항목
5. ~/.triple-crown/ 벤더 디렉터리
6. ~/.claude/skills/ 의 .triple-crown-skill 마커 디렉터리  → 현재 0개, 확인만
```

### 2.3 영향 고지

2번은 사용자의 **전역** `CLAUDE.md`다. 제거하면 모든 프로젝트에서 Triple Crown 라우팅 정책(GSD 소유권, superpowers 허용/금지 목록, 권한 순서, ship 소유권)이 사라진다. `crew:managed-routing` 블록이 재설치되기 전까지 공백이 생긴다.

- `works/harness`는 GSD_CONTROLLED가 아니므로(`.planning/STATE.md` 부재) 이 프로젝트에는 무해
- 다른 프로젝트에서 GSD 라이프사이클을 진행 중이라면 영향 있음 → §2.1.1 사전 점검으로 확인

**공백 구간을 명시적으로 관리한다.** 제거 시점부터 `crew:managed-routing` 재설치까지는 ship 가드와 라우팅 정책이 없는 상태다. 이 구간은 M0~M7 전체가 아니라 **M1a 완료 시점까지**로 한정한다 — M1a에서 `crew-ship-guard.cjs` 와 `crew:managed-routing` 블록이 새 이름으로 다시 설치 가능해지므로, M1a 통과 직후 `crew install --project <실제 프로젝트 경로>` 로 보호를 복원한다. **이 복원 설치는 M-1의 `$HOME` 루트 거부(§2.0 4번)가 존재함을 전제로 한다** — 없으면 D13 재현이다. M1a가 예상보다 길어지거나 중단되면 §2.5 복구로 구 보호를 되돌린다.

### 2.4 완료 판정

제거가 끝났음의 판정과, **되돌릴 수 있음**의 판정을 모두 요구한다.

제거 확인:

```
~/.gsd/capabilities/           비어 있음
~/.claude/settings.json        triple-crown 훅 항목 없음 (그 외 사용자 항목은 보존)
~/CLAUDE.md                    managed-routing 마커 없음 (마커 밖 사용자 작성분 보존)
~/.triple-crown/               없음
~/.claude/hooks/               triple-crown-ship-guard.cjs 없음
```

복구 가능성 확인 (제거 후 즉시 1회 리허설):

```
scripts/legacy-backup.cjs verify   MANIFEST.json 의 sha256 이 archive.tar.gz 내용과 일치
scripts/legacy-backup.cjs restore --dry-run
                                   복구 대상 경로·충돌 목록 출력, 실제 쓰기 없음
```

`git push` 가 더 이상 차단되지 않는 것은 **성공 지표가 아니라 보호 공백의 증상**이다. 완료 판정에서 제외하고, §2.3의 공백 구간 관리 항목으로만 다룬다.

### 2.5 복구 절차

M0~M7 중 어느 시점에서든 중단·실패 시:

```
scripts/legacy-backup.cjs restore --from ~/.crew-legacy-backup/2026-08-20
```

동작:

1. `MANIFEST.json` 의 sha256 을 아카이브와 대조. 불일치면 즉시 중단
2. 복구 순서대로 디렉터리·파일 원복 (`~/.triple-crown/` → capabilities → hooks)
3. `~/CLAUDE.md` 는 전체 덮어쓰기가 아니라 `CLAUDE.md.fragment` 를 원래 위치에 재삽입. 그 사이 사용자가 추가한 내용은 보존
4. `~/.claude/settings.json` 은 **의미 기반 술어로 재삽입**한다. 아래 §2.5.1 참조
5. 복구 후 `gsd-tools capability list` 로 3개 재등록 확인

### 2.5.1 settings.json 복구 충돌 정책

v1.2는 JSON Pointer 위치에 원본 값을 재삽입한다고 썼다. **틀렸다.** 제거 후 사용자가 `hooks.PreToolUse` 배열을 편집하면 인덱스가 밀려 다른 훅을 침범하거나 중복이 생긴다.

기존 설치자가 이미 올바른 방식을 쓰고 있다 — 복구도 그것을 따른다:

| 위치 | 방식 |
|---|---|
| `bin/triple-crown.cjs:404 removeShipGuard` | `command` 에 `triple-crown-ship-guard.cjs` 가 포함된 훅을 가진 그룹을 `filter` 로 제거 |
| `scripts/install-claude-ship-guard.cjs:58` | `matcher==='Bash'` 이고 command 가 일치하는 그룹이 **없을 때만** push (멱등) |
| 동 `:25-29 migrateLegacyRegistrations` | 술어로 찾아 in-place 치환 |

셋 다 **술어 기반이고 인덱스를 쓰지 않는다.**

복구 절차:

```
1. 현재 ~/.claude/settings.json 의 sha256 == 백업 sha256
   → 백업 이후 변경 없음. 파일 전체 복원해도 안전
2. 다르면 파일을 덮어쓰지 않는다. 대신 의미 기반 재삽입:
   a. hooks.PreToolUse 가 배열이 아니거나 JSON 파싱 실패
      → 충돌 보고 후 중단. 자동 쓰기 없음. 수동 복구 안내 출력
   b. command 에 ship-guard 스크립트명이 포함된 그룹이 이미 존재
      → 아무것도 하지 않음 (멱등)
   c. 없으면 settings.json.hookgroup 의 객체를 배열 끝에 push
3. 다른 배열 요소는 절대 건드리지 않는다. 인덱스를 참조하지 않는다
```

`~/CLAUDE.md` 복구가 마커 쌍 기반인 것과 같은 원리다 — **위치가 아니라 정체로 찾는다.**

**대안 복구**: M1a까지 진행된 상태라면 구 설치를 되돌리는 대신 `crew install` 로 새 보호를 설치하는 쪽이 낫다. 두 경로 모두 유효하며, 판단 기준은 M1a 통과 여부다.

## 4. M0 — 공유 lib 빌드 파이프라인 + 설치 ref 고정

### 4.1 문제

`${GSD_CAP_DIR}`은 해당 capability **자신의** 디렉터리만 가리킨다. capability를 9개로 분해하면 `crew-quality`의 게이트가 `crew-core`의 `repo-state-lib.cjs`를 참조할 수 없다.

상위 문서 §5.2가 검토한 3안 중 **A(패키징 시 복제)** 채택. 런타임 결합 0, 소스 중복 0.

### 4.2 `scripts/build-capabilities.cjs`

canonical lib를 정상 수정한 경우와 사본을 수동 편집한 경우를 **구분해야 한다.** 둘 다 "사본 해시가 canonical과 다름"으로 보이므로 단순 비교로는 갈라낼 수 없다. 직전 생성 기록을 제3의 기준점으로 쓴다.

세 값을 비교한다:

| 기호 | 의미 |
|---|---|
| `new` | 지금의 `lib/<f>.cjs` sha256 |
| `prev` | 해당 capability의 `LIB-HASH.json` 에 기록된 직전 생성 해시 |
| `copy` | 지금의 `capabilities/<id>/checks/lib/<f>.cjs` sha256 |

판정:

```
사본 없음                      → 복사. LIB-HASH 에 new 기록
copy == new                    → 최신. 기록만 확인하고 통과
copy == prev  (그리고 != new)  → canonical 정상 수정. 덮어쓰고 new 기록
copy != prev  && copy != new   → 사본 수동 편집. non-zero exit
LIB-HASH 없고 사본 == canonical → 최초 도입(부트스트랩). 기록만 새로 쓴다
LIB-HASH 없고 사본 != canonical → 출처 증명 불가. non-zero exit
표에 없는 사본                  → non-zero exit. 삭제는 --prune 명시 시에만
```

부트스트랩 행이 필요한 이유: M0 Task 2 가 사본을 심고 Task 3 이 첫 빌드를 도는 순간이
정확히 "사본은 있는데 기록은 없는" 상태다. 무조건 거부하면 최초 빌드가 영영 불가능하다.

`prev` 를 기준으로 삼기 때문에 canonical 을 몇 번을 수정해도 빌드가 막히지 않는다. 막히는 경우는 사본을 직접 건드린 경우 하나뿐이다.

실패 메시지는 어느 capability의 어느 사본이 어긋났는지와 복구 명령(`git restore <사본경로>` 후 재빌드)을 출력한다.

### 4.3 연결 지점

| 지점 | 변경 |
|---|---|
| `package.json` | `scripts.prepack` 에 연결 → `npm pack` 전 자동 실행 |
| `package.json` | `scripts["build:caps"]` 추가 → 개발 중 수동 실행 |
| `bin/crew.cjs` `validateBundledManifests()` | LIB-HASH 대조 검사 추가 |
| capability 게이트 command | `${GSD_CAP_DIR}/checks/lib/repo-state-lib.cjs` 참조 |

### 4.4 완료 판정

| 시나리오 | 기대 |
|---|---|
| `lib/repo-state-lib.cjs` 수정 → 빌드 없이 계약 테스트 | **실패** (drift 검출) |
| 위 상태에서 `npm run build:caps` → 계약 테스트 | 통과 |
| **canonical 수정 → `npm pack --dry-run`** | **성공** — `prepack` 이 사본을 갱신하므로 막히지 않는다 |
| canonical 2회 연속 수정 → 매번 빌드 | 매번 성공 (`prev` 기준 판정) |
| 사본 `capabilities/<id>/checks/lib/*.cjs` 직접 수정 → 빌드 | **실패** + 복구 명령 출력 |
| `npm pack --dry-run` 산출물 | 각 capability의 `checks/lib/` 포함 |

3·4행이 이 절의 회귀 방지선이다. L1 `lib-hash` 테스트에 두 시나리오를 그대로 넣는다.

### 4.5 설치 진입점 고정 — 부트스트랩 자기일관성 + 프리릴리스 차단

v1.1의 이 절은 **성립하지 않았다.** 세 가지가 동시에 틀렸다.

**문제 1 — 태그 안 스크립트는 불변 객체다.** v1.1은 "문서의 curl 원라이너를 `.../v0.6.4/install.sh` 로 바꾼다"고 했다. 실측:

```
git show v0.6.4:install.sh   →   34:REF="${TRIPLE_CROWN_REF:-main}"
```

`v0.6.4` 태그 안 스크립트의 기본 ref는 이미 `main` 으로 굳어 있다. `main` 의 사본을 고쳐도 저 값은 변하지 않는다. 즉 `curl .../v0.6.4/install.sh | bash` 는 **여전히 `main` 을 설치한다.** 자기 자신을 가리키지 못하는 순환이었다.

**문제 2 — npx 직접 경로는 `install.sh` 를 거치지 않는다.** `README.md:29`·`41`·`112`·`127`·`128` 이 ref 없는 형태를 문서화한다:

```
npx --yes github:ungkey/triple-crown install --yes
```

ref 생략은 기본 브랜치(`main`)로 해석된다. `install.sh` 를 아무리 고쳐도 이 경로는 막히지 않는다. (`README.md:35` 에 `#v0.6.4` 고정형이 있지만 선택지 중 하나일 뿐이다.)

**문제 3 — 릴리스 순서가 뒤집혀 있었다.** v1.1은 `v0.7.0` 태그를 만든 뒤 상수를 갱신하라고 했다. 그러면 `v0.7.0` 태그 안 스크립트의 기본 ref는 아직 이전 값이다. 문제 1과 같은 오류의 재발이다.

#### 해결 — 2계층

**계층 1: 부트스트랩 자기일관성 불변식**

> `install.sh`·`install.ps1` 의 기본 ref는 **자신이 담겨 배포되는 태그와 같아야 한다.**

이를 만족시키는 순서는 하나뿐이다 — **상수·문서 갱신 커밋 → 검증 → 그 커밋에 태그.** 태그를 먼저 찍으면 항상 어긋난다.

`v0.6.4` 는 이미 어긋났고 소급 수정이 불가능하므로 M-1에서 **`v0.6.5` 를 새로 만든다**:

**불변식은 스크립트만이 아니라 문서에도 적용된다.** 태그 안 README가 ref 없는 npx 예시를 안내하면, 사용자는 고정된 부트스트랩을 우회해 `main` 을 설치한다. 스크립트 상수와 문서 예시는 **같은 커밋**에서 갱신되어야 한다.

| 순서 | 작업 |
|---|---|
| 1 | **한 커밋에** — `install.sh`·`install.ps1` 기본 ref 상수를 `v0.6.5` 로, **그리고** README·docs 의 curl 원라이너를 `.../v0.6.5/install.sh` 로, 모든 npx 예시를 `#v0.6.5` 로 변경 |
| 2 | L1 `install-entrypoints` 통과 확인 — 스크립트 상수와 문서 예시를 **같은 트리에서 동시에** 검사한다 |
| 3 | **그 커밋에** `v0.6.5` 태그 |

1번 커밋 시점에 문서는 아직 존재하지 않는 태그를 가리킨다. 3번에서 바로 그 커밋에 태그가 찍히면서 자기일관이 된다. 순서를 바꾸면(태그 먼저) 태그 안 문서가 영구히 어긋난다 — 문제 1과 같은 오류다.

이후 `main` 의 기본 ref는 M0~M7 내내 `v0.6.5` 를 가리킨다. `curl .../main/install.sh` 로 받아도 안정 릴리스가 설치된다.

최종 릴리스도 같은 순서다: **상수 + 문서 예시를 `v0.7.0` 으로 바꾸는 한 커밋** → 검증 → **그 커밋에** `v0.7.0` 태그.

**계층 2: 진입점 무관 프리릴리스 차단**

계층 1은 `install.sh` 를 거치는 경로만 덮는다. npx 직접 실행·로컬 tgz·`--package` 형태까지 전부 막으려면 **설치자 자신이 거부**해야 한다.

M-1에서 `bin/triple-crown.cjs` 에 추가:

```
VERSION 이 프리릴리스(하이픈 포함: -dev / -alpha / -rc …)이고
--allow-prerelease 가 없으면  →  설치 거부, non-zero exit
```

M0 첫 커밋에서 `VERSION` 과 `package.json.version` 을 `0.7.0-dev` 로 올린다. 그 순간부터 `main` 에서 나온 산출물은 **어느 진입점으로 들어오든** 설치가 거부된다. 최종 릴리스 커밋에서 `0.7.0` 으로 내리면 다시 열린다.

`bin/triple-crown.cjs:11` 이 이미 `VERSION` 파일을 읽고 `:70 versionTuple()` 이 존재하므로 파싱은 재사용한다.

#### L1 `install-entrypoints` 계약 테스트

| 단언 | 대상 |
|---|---|
| 기본 ref 상수가 브랜치명(`main`/`master`)이 아님 | `install.sh` · `install.ps1` |
| 릴리스 커밋에서 기본 ref 상수 == 그 커밋에 찍을 태그 | 동상 |
| 문서의 모든 `npx … github:` 예시와 curl 원라이너에 `#<태그>`/`/<태그>/` 포함, 그 태그 == 스크립트 상수 | `README.md` · `docs/**` |
| `VERSION` 이 프리릴리스면 `install` non-zero, `--allow-prerelease` 면 진행 | `bin/triple-crown.cjs` |

**개명·경로 치환 시점**: `TRIPLE_CROWN_REF` → `CREW_REF`, `ungkey/triple-crown` → `ungkey/crew` 는 M1a 개명표(§5.1)에서 한다. M-1은 개명 단계가 아니므로 기본값과 거부 로직만 넣는다. 저장소 개명 후 GitHub이 구 경로 리다이렉트를 유지하므로 기존 태그 참조는 계속 해석되지만, 리다이렉트에 의존하지 않도록 M1a에서 문서 경로를 함께 바꾼다.

## 5. M1 분할 — 4개 하위 단계

상위 문서 M1이 5가지를 묶어 단일 단계로는 너무 크다. 회귀 원인 특정을 위해 분할한다.

| 하위 | 범위 | 통과 조건 |
|---|---|---|
| **M1a** | 기계적 개명만 — 문자열 치환 + 디렉터리·파일명 변경. **분해 없음** | 기존 e2e 전부 통과. 기능 변화 0 |
| **M1b** | capability 4개로 분해 (`crew-ship` 분리, M0 산출물 사용). `crew-security` 는 GSD 1.11.0 제약으로 보류 | L1 계약 테스트 통과, `crew doctor` READY |
| **M1c** | `crew uninstall-legacy` 명령 구현 | 픽스처에 구 설치를 심고 6곳 제거 확인 |
| **M1d** | doctor 검사 2건 | 각 조건 재현 시 검출 |

**M1a가 통과해야 M1b에 진입한다.**

#### M1a 시점의 capability 이름 (중간 상태)

M1a는 분해하지 않으므로 capability는 **3개 그대로**다. 상위 문서 §4.3의 매핑(`triple-gstack` → `crew-quality`/`crew-security`/`crew-ship`)은 분해를 전제하므로 M1a에는 적용할 수 없다. M1a는 1:1 개명만 한다:

| M1a 개명 | 비고 |
|---|---|
| `triple-gstack` → `crew-quality` | 이 시점에는 여전히 God capability. M1b에서 분해의 출발점이 된다 |
| `triple-superpowers` → `crew-discipline` | 1:1 |
| `triple-crown-guide` → `crew-guide` | 1:1 |

M1b는 `crew-quality`에서 **`crew-ship` 하나만** 떼어내 총 **4개**(`crew-discipline` / `crew-quality` / `crew-ship` / `crew-guide`)로 만든다. 9개 분해는 **GSD 1.11.0에서 성립하지 않는다** — `gsd-core src/capability-source.cts:836` 이 검증 맵을 `new Map([[id, cap]])`, 즉 **설치 중인 capability 하나뿐**으로 만들기 때문에 교차 capability `requires` 는 대상이 이미 active 여도 `requires "X" which does not exist` 로, 교차 capability `consumes` 는 `never produced by any host artifact or capability hook` 으로 거부된다(둘 다 실측). 나머지는 각자 시점에 만든다:

| capability | 시점 | 근거 |
|---|---|---|

## 6. 테스트 3계층

D10(mock 전용 테스트)이 D3을 놓친 원인이다. 계층을 나눠 각각이 다른 부류를 잡게 한다.

### L1 — 계약 테스트 (`e2e/contract/`)

- 실행: 매 커밋 · 수 초 · 비용 0
- 언어: Node CJS (기존 `e2e/*.cjs` 와 일관)

|---|---|---|

**halt 예측 원리**: D3의 halt는 Claude 세션 안에서 일어난다(`plan-phase.md:1450`의 워크플로 분기). CLI로 직접 재현할 수 없다. 그러나 `blocking: true` + 게이트 스크립트 non-zero exit 조합이면 halt가 확정이므로, 이 조합을 단언하면 결정적으로 검출된다. `assert-hooks.cjs`(67줄)가 이미 이 형태다.

### L2 — headless 스모크 (`e2e/headless/`, `fixtures/tiny/`)

- 실행: **M1b 이후 매 M 단계 완료 시** 자동. M0·M1a는 설치 가능 산출물의 동작 변화가 없어 L1만 돌린다 (비용 낭비 방지)

#### 하드닝 플래그는 쓸 수 없다 (실측)

`claude --help` 실측 결과, 통상적인 하드닝 수단이 전부 L2의 목적과 충돌한다.

| 플래그 | 실제 동작 | L2 적용 |
|---|---|---|
| `--safe-mode` | CLAUDE.md · **skills · plugins · hooks** · MCP · custom commands 전부 비활성 | **불가** — 스킬과 게이트 훅이 곧 검증 대상 |
| `--bare` | **hooks 건너뜀**, plugin sync · CLAUDE.md 자동탐색 생략 | **불가** — 게이트 훅이 안 돌면 D3 부류를 못 잡는다 |
| `--setting-sources` 에서 `project` 제외 | 프로젝트 훅·권한 미로딩 | **불가** — GSD 설치 산출물이 프로젝트 훅이다 |

L2는 훅과 스킬이 **전부 살아 있는** Claude Code 를 요구한다. 프로세스 내 하드닝으로 얻을 수 있는 것이 거의 없다는 뜻이다.

#### 신뢰 경계 (명시)

v1.1은 이 절을 "격리 계약(필수)"이라 불렀다. **그 표현을 철회한다.** `node` 실행이 허용되는 한 임의 파일·네트워크 접근은 원리적으로 가능하며, 허용목록은 그것을 막지 못한다.

L2의 실제 성격은 **신뢰된 픽스처 전용 실행**이다:

- 입력(`fixtures/tiny/`)은 이 저장소가 작성하고 리뷰한다. 외부 입력을 태우지 않는다
- 허용목록은 샌드박스가 아니라 **"이 픽스처가 필요로 하는 명령이 그대로인가"를 보는 회귀 검사**다
- 보안 격리가 필요하다면 아래 선택 스위치를 켠다

#### HOME 대체 — 밀폐 설치

호스트 HOME 을 그대로 쓰면 `~/.ssh` · `~/.npmrc` · `~/.config/gh` · `~/.gitconfig` 가 전부 열린다. 임시 HOME 을 만들고 필요한 것만 채운다.

```
$TMP/home/
  .claude/.credentials.json   호스트에서 복사 — Claude 인증에 필수
  .claude/gsd-core/           gsd-core 신규 설치
  .gsd/capabilities/          crew install 산출물
```

호스트 의존은 실측 확인했다: `~/.claude/gsd-core/`, `~/.gsd/`, `~/.claude/.credentials.json`.

부수 효과가 목적에 부합한다 — L2가 **신선한 설치 위에서** 돌게 되므로 설치자 산출물까지 함께 검증된다. 노출되는 호스트 자격증명은 Claude 인증 하나로 줄어든다(이것 없이는 실행 자체가 불가능).

#### git 신원 시드 (필수)

전역 gitconfig 를 임시 파일로 갈아끼우면 신원이 사라진다. 실측:

```
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null git commit -m t
  →  Author identity unknown  /  *** Please tell me who you are.
```

L2는 하네스의 픽스처 초기 커밋과 GSD executor 의 원자 커밋을 **둘 다** 만든다. 신원이 없으면 첫 커밋에서 즉시 죽는다. 임시 `GIT_CONFIG_GLOBAL` 에 테스트 전용 신원을 시드한다:

```ini
[user]
    name = Triple Crown E2E
    email = triple-crown-e2e@example.invalid
```

`e2e/run-live.cjs:57-58` 이 이미 같은 값을 repo-local 로 설정한다. 하네스는 **상수를 한 곳에 두고** 전역·repo-local 양쪽에 심는다(repo-local 은 안전망). M1a 기계적 개명이 이 상수도 `Crew E2E` / `crew-e2e@example.invalid` 로 함께 바꾼다.

`.invalid` 는 예약 TLD 라 실제 메일로 나갈 수 없다.

#### 실행 계약

| 통제 | 수단 |
|---|---|
| 권한 모드 | `--permission-mode acceptEdits` — `bypassPermissions` 는 쓰지 않는다 |
| 도구 허용목록 (argv 고정) | `Read Edit Write Glob Grep` + `Bash(git status)` `Bash(git add -A)` `Bash(git commit -m *)` `Bash(git rev-parse *)` `Bash(git diff *)` `Bash(node --test *)`. **`node *` 와 `npm *` 는 제외** — 픽스처 테스트를 `node --test` 로만 돌려 npm lifecycle script 실행 경로를 없앤다 |
| 도구 거부목록 | `--disallowedTools "WebFetch WebSearch"` |
| MCP 차단 | `--strict-mcp-config`, `--mcp-config` 미지정 — Gmail·Drive·Figma 등 미로딩 |
| 설정 소스 | `--setting-sources project` — 임시 HOME 이므로 user 설정은 애초에 비어 있다 |
| 작업 경로 | `mktemp -d` 아래 픽스처 사본. 저장소 원본은 읽기 전용 |
| env | `GITHUB_TOKEN`·`GH_TOKEN`·`NPM_TOKEN`·`AWS_*`·`ANTHROPIC_API_KEY` 삭제. `HOME` 을 임시 HOME 으로, `GIT_CONFIG_GLOBAL`·`GIT_CONFIG_SYSTEM` 을 임시 파일로 (아래 신원 시드 필수) |
| 시간 상한 | `--max-turns` 가 없으므로(§1.3) 벽시계 상한 강제. 초과 시 **프로세스 그룹** 종료 (`detached: true` + `process.kill(-pid, 'SIGKILL')`) |
| 감사 | `--output-format stream-json` 전량을 `HEADLESS-LOG.jsonl` 로 보존. 실행된 Bash 명령 전체를 결과에 목록화 |

**미실측 항목**: 허용목록 밖 Bash가 비대화형에서 즉시 오류로 끝나는지, 대기하다 타임아웃되는지는 확인하지 않았다. M1b에서 거부 대상 명령 1건으로 실험해 확정하고 L1 계약으로 고정한다.

#### 선택 스위치 — `CREW_L2_ISOLATE=container`

실제 OS 격리가 필요하다고 판단되면 같은 러너를 컨테이너에서 돌린다. **기본값은 꺼짐**이다.

- 기본을 끈 근거: 이 머신에 `bwrap`·`podman` 은 없고 `docker` 는 Docker Desktop 경유(`/mnt/c/...`)라 WSL 파일시스템 마운트 비용이 매 M 단계마다 붙는다
- 켰을 때: 호스트 홈 미마운트, 작업 경로만 rw 마운트, egress 는 Anthropic API 엔드포인트만 허용
- **L3는 이 스위치가 기본 켜짐**이다 — 실행 빈도가 낮아 비용을 감당할 수 있다

#### 단언

1. 종료 JSON이 정상 완료를 보고
2. `.planning/STATE.md` 에 `needs_human` 섹션 부재
3. phase 2개 모두 완료 상태
4. 사람 입력 요구 흔적 부재
5. **감사 로그의 Bash 명령이 전부 허용목록 안** — 벗어난 시도가 1건이라도 있으면 실패. 4번이 "무엇이든 승인 없이 실행됐다"로 만족되는 것을 막는 대칭 단언
6. **임시 HOME 밖 경로에 대한 쓰기 없음** — 감사 로그의 파일 도구 대상 경로를 검사
7. **픽스처 초기 커밋이 성공** — 신원 시드 회귀 검사. 이 단언이 실패하면 이후 단언은 전부 무의미하므로 가장 먼저 판정한다

L1이 못 잡는 것 — 워크플로 마크다운이 게이트 결과를 오해하는 부류 — 을 잡는다.

| 백업 도구 부재로 안전한 정리 불가 | M-1 준비 커밋(§2.0)이 `legacy-backup.cjs` 를 먼저 만든다 |
| 태그 안 문서가 ref 미고정 상태로 굳음 | §4.5 — 스크립트 상수와 문서 예시를 같은 커밋에서 갱신 후 태그 |
| 임시 HOME 에서 커밋 실패 (`Author identity unknown`) | §6 git 신원 시드 + 단언 7 (초기 커밋 성공) |
| settings 복구가 사용자 훅을 침범 | §2.5.1 — sha256 대조 후 불일치 시 술어 기반 재삽입, 파싱 실패 시 중단 |
| L2를 격리로 오인 | §6 신뢰 경계 명시 — 신뢰된 픽스처 전용. 실제 격리는 `CREW_L2_ISOLATE=container` |
| 레거시 제거 후 복구 불가 | §2.1 매니페스트 백업 + §2.5 복구 스크립트 + 제거 직후 `restore --dry-run` 리허설 |
| 보호 공백이 장기화 | §2.3 — 공백을 M1a 완료까지로 한정, 통과 즉시 `crew install` 로 복원 |
| canonical lib 정상 수정이 `prepack` 을 막음 | §4.2 3-way 판정 (`prev` 기준) + §4.4 3·4행 회귀 테스트 |
| headless 에이전트의 자격증명·네트워크 접근 | §6 HOME 대체(노출은 Claude 인증 1건) + argv 고정 허용목록 + 단언 5·6. 완전 차단은 컨테이너 스위치 |
| GSD 1.11.0 단일 항목 capMap 이 교차 capability `requires`·`consumes` 를 거부 | 전 capability `requires: []`, 아티팩트 사슬로 묶인 step 은 같은 capability 유지(§5), L1 `capability-split` 펜스 8종 |
