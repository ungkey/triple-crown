# v0.6.4 Hotfix — skills were never visible to Claude Code

## Symptom

`triple-crown install` reported success, `triple-crown doctor` reported
`READY=true PASS=13 WARN=0 FAIL=0`, and `gsd-tools capability list` reported
`status=active, surfaced=true` for all three capabilities — yet Claude Code never
listed `/gsd-triple-crown` or any `/gsd-triple-gstack-*` skill.

## Root cause

Two independent defects, both fatal on a clean machine.

### 1. `capability install` never writes a SKILL.md into any skills root

In GSD 1.10 the capability install path only unpacks the bundle into
`.gsd/capabilities/<id>/`. Skill files reach a runtime skills root exclusively
through `surface.applySurface()`, and the only CLI entry point that calls it is
`gsd-tools capability set <id> --runtime <r>` — the `--runtime` flag is what
turns on `materialize`. `capability install`, `capability enable`, and
`capability disable` all leave the skills root untouched.

`surfaced: true` in `capability list` is a registry computation, not evidence
that a file exists on disk. Triple Crown's doctor trusted that field.

### 2. A project-scoped capability can never surface a skill

`install-profiles.cjs → readInstalledCapabilitySkill()` resolves third-party
skill sources from a hardcoded global path:

```js
const home = process.env['GSD_HOME'] || os.homedir();
const capDir = path.join(home, '.gsd', 'capabilities', capId);
```

Triple Crown installs with `--scope project`, so its bundles live in
`<project>/.gsd/capabilities/` — a directory this reader never consults.

Switching to `--scope global` would make the skills appear, but a globally
installed `triple-gstack` activates all 9 of its gates and steps in **every**
repository on the machine, including ones with no `.planning/STATE.md`. That
trade was rejected.

## Fix

The installer now copies the bundled skills into the target project's own
`.claude/skills/` directory, using the same `gsd-` prefixed directory names the
SKILL.md frontmatter already declares:

```text
<project>/.claude/skills/gsd-triple-crown/SKILL.md
<project>/.claude/skills/gsd-triple-gstack-code-review/SKILL.md
<project>/.claude/skills/gsd-triple-gstack-qa-only/SKILL.md
<project>/.claude/skills/gsd-triple-gstack-cso/SKILL.md
<project>/.claude/skills/gsd-triple-gstack-post-ship/SKILL.md
<project>/.claude/skills/gsd-triple-gstack-release-observe/SKILL.md
```

Capabilities stay project-scoped, so gates never leak into unrelated
repositories, and the installer no longer depends on GSD's internal surface
pipeline.

Each installed directory carries a `.triple-crown-skill` ownership marker.
Uninstall removes exactly the marked directories; a hand-authored `gsd-*` skill
in the same folder is preserved, and install refuses to overwrite an unmarked
directory.

Both bundled skill families already resolved their capability directory from
project **and** global locations, so no SKILL.md body changed.

## Fix — ship guard was inert

`scripts/install-claude-ship-guard.cjs` copied the guard with `fs.copyFileSync`
and registered it as a bare path:

```json
"command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/triple-crown-ship-guard.cjs"
```

No file in the repository carries an executable bit, and npm does not invent one,
so the hook died with a permission error on every Bash tool call. On Windows the
shebang is meaningless regardless of mode. The v0.5 ship-ownership policy was
therefore unenforced in every installation.

Now the installer `chmod 0755`s the copied guard **and** registers it through an
explicit interpreter:

```json
"command": "node \"$CLAUDE_PROJECT_DIR/.claude/hooks/triple-crown-ship-guard.cjs\""
```

Existing installations are migrated in place: any PreToolUse entry referencing
`triple-crown-ship-guard.cjs` is rewritten to the new command on the next
install, without creating a duplicate group.

## Doctor

Four checks added:

| check | meaning |
|---|---|
| `skills-installed` | every bundled skill has a `SKILL.md` under `<project>/.claude/skills` — FAIL when Claude Code cannot see them |
| `skills-no-global-shadow` | WARN when a stale `~/.claude/skills/gsd-triple-*` copy could shadow the project version |
| `ship-guard-exec` | the copied guard carries an executable bit |
| `ship-guard-registered` | the PreToolUse command runs through `node` |

## Tests

The existing smoke suite ran entirely against `tests/fake-gsd.cjs`, which writes
a JSON ledger and nothing else, so neither defect was observable. Added
assertions:

- installed skill directories exist, and each SKILL.md's frontmatter `name`
  matches its directory name
- ownership marker present on every managed skill directory
- guard file is executable and registered with a `node` prefix
- uninstall removes managed skills and preserves an unmanaged `gsd-*` skill

## Known limitation (unchanged)

`guards/triple-crown-ship-guard.cjs` classifies protected commands with regular
expressions over the Bash command string. Forms such as `git -C <dir> push`,
shell aliases, or `eval`-wrapped invocations are not matched. The guard is a
workflow-ownership guardrail, not a security boundary.
